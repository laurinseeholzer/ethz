\section{Dynamic Memory Allocation}

\begin{definition}
    \textbf{Static vs Automatic Memory Allocation:} Global variables are statically allocated when the program is loaded and deallocated when it exits, while function variables are automatically allocated on function call and deallocated on return.
\end{definition}

\begin{remark}
    Note that because automatically allocated memory is created on function calls, it is stored on the stack.
\end{remark}

\begin{remark}
    Often we need a larger amount of memory space that persists across multiple function calls without lasting the entire program lifetime.
\end{remark}

\begin{definition}
    \textbf{Dynamic Memory Allocation:} We can use allocation functions (such as \texttt{malloc}) to explicitly request dynamic memory blocks on the heap.
\end{definition}

\begin{codeexample}
char *a = (char *) malloc(10 * sizeof(char)); // Allocates uninitialized memory for 10 characters
char *zeros = (char *) calloc(10, sizeof(char)); // Allocates zero-initialized memory for 10 characters
free(a); // Frees allocated memory block

zeros = (char *) realloc(zeros, 20 * sizeof(char)); // Resizes allocated memory block to 20 characters
\end{codeexample}

\begin{definition}
    \textbf{Memory Corruption:} Occurs when a program unintentionally reads, modifies, or overwrites memory contents outside the bounds of an allocated block, or writes to memory that has already been deallocated or belongs to allocator metadata. This causes unpredictable program behavior, silent data corruption, or segmentation faults.
\end{definition}

\begin{definition}
    \textbf{Memory Leaks:} Occur when dynamically allocated heap memory is no longer referenced by any active pointer in the application but has not been returned to the heap via \texttt{free()}. Over time, uncollected memory accumulates and exhausts available memory.
\end{definition}

\begin{important}
    In C, memory management is strictly manual: every byte allocated on the heap must eventually be deallocated exactly once. Failing to properly manage memory boundaries and lifetimes leads to either memory corruption or memory leaks.
\end{important}

\subsection{Data Structures}

\begin{definition}
    \textbf{Structured Data} is a custom type containing multiple data fields of different types. It is defined using the \texttt{struct} keyword.
\end{definition}

\begin{codeexample}
struct myData {
    int dataField;
    char dataName;
};
\end{codeexample}

\begin{definition}
    \textbf{Unions} overlay multiple member fields in a single shared memory location. Only one member value should be stored/interpreted at a time, and C performs no runtime tracking of the active member type.
\end{definition}

\begin{codeexample}
union currentTime {
    char stringName[10];
    int intTime;
    long longTime;
};
\end{codeexample}

\begin{remark}
    We can use \texttt{typedef} to define type aliases. Mixing struct tags and typedef aliases with the same name can cause confusion.
\end{remark}

\begin{remark}
    Tags (e.g., \texttt{struct tag \{...\}}) belong to a separate namespace from typenames; consequently, a typename and a tag can share the same identifier.
\end{remark}

\begin{remark}
    Structs and pointers allow building \textbf{dynamic data structures}. Using \texttt{void} pointers allows elements to be generic.
\end{remark}

\begin{codeexample}
struct listNode {
    void *value;
    struct listNode *next;
};

struct listNode *myList = NULL;
\end{codeexample}

\subsection{Memory Allocators}

\begin{definition}
    \textbf{Implicit vs. Explicit Allocators:}
    \begin{itemize}
        \item \textbf{Explicit Allocator:} The application program explicitly allocates and deallocates memory blocks (e.g., \texttt{malloc} and \texttt{free} in C, \texttt{new} and \texttt{delete} in C++).
        \item \textbf{Implicit Allocator (Garbage Collector):} The application explicitly requests memory allocation, but deallocation is handled automatically by the runtime system when a block is no longer in use or reachable (e.g., in Java, Python, Go, and Lisp).
    \end{itemize}
\end{definition}

\begin{remark}
    \textbf{Allocator Constraints and Requirements:}
    \begin{itemize}
        \item \textbf{Arbitrary request sequences:} The allocator cannot make assumptions about the ordering or interleaving of allocation and deallocation requests.
        \item \textbf{Immediate response:} Requests must be serviced immediately; the allocator cannot buffer or reorder requests to optimize placement.
        \item \textbf{Heap storage only:} Any metadata structures used by the allocator must reside directly within the heap itself.
        \item \textbf{Alignment requirements:} Blocks must satisfy architecture-specific alignment boundaries (e.g., 8-byte alignment on 32-bit systems, 16-byte alignment on 64-bit systems).
        \item \textbf{Non-relocatable blocks:} Once allocated, blocks cannot be moved, compacted, or relocated by the allocator.
    \end{itemize}
\end{remark}

\begin{definition}
    \textbf{Performance Goals:} Allocator efficiency is governed by two competing metrics: Throughput and memory utilization.
\end{definition}

\begin{definition}
    \textbf{Internal vs. External Fragmentation:}
    \begin{itemize}
        \item \textbf{Internal Fragmentation:} Occurs when an allocated block is larger than the requested payload. Caused by allocator metadata overhead (headers, footers), alignment padding, or minimum block size constraints. It depends solely on individual request sizes and allocator overhead, making it easy to quantify.
        \item \textbf{External Fragmentation:} Occurs when there is sufficient aggregate free memory in the heap to satisfy an allocation request, but no single contiguous free block is large enough. It depends on the future history of requests and is significantly harder to measure and avoid.
    \end{itemize}
\end{definition}

\begin{definition}
    \textbf{Block Structure and Header:} Because \texttt{free(ptr)} receives only a pointer without the block size, each block stores metadata preceding the payload:
    \begin{itemize}
        \item \textbf{Header:} A single word (4 or 8 bytes) placed immediately before the user payload containing:
        \begin{itemize}
            \item \textbf{Block Size:} The total size of the block (including header, payload, and padding).
            \item \textbf{Allocated Bit:} Since blocks are aligned to multiples of 8 (or 16) bytes, the lowest 3 (or 4) bits of any valid block size are always zero. The allocator repurposes the least significant bit (LSB) as an allocation flag: \texttt{1} for allocated, \texttt{0} for free.
        \end{itemize}
        \item \textbf{Payload:} The user-accessible memory returned by \texttt{malloc}.
        \item \textbf{Padding:} Optional unused space to satisfy alignment constraints.
    \end{itemize}
\end{definition}

\subsubsection{Tracking Free Blocks}

\begin{definition}
    \textbf{Implicit Free List:} All blocks (both allocated and free) are chained together implicitly through the size fields in their headers. Traversing blocks requires scanning sequentially from the beginning of the heap.
\end{definition}

\begin{definition}
    \textbf{Explicit Free List:} Links only the \emph{free} blocks into an explicit doubly linked list by storing \texttt{prev} and \texttt{next} pointers inside the unused payload area of each free block.
\end{definition}

\begin{definition}
    \textbf{Segregated Free Lists:} Maintains an array of distinct free lists partitioned by size class (e.g., small exact classes like $16, 24, 32$ bytes, followed by power-of-two ranges like $33\text{--}64$, $65\text{--}128$, etc.).
\end{definition}

\begin{definition}
        \textbf{Coalescing:} When a block is freed, it must be merged with adjacent free blocks to prevent false fragmentation (consecutive small free blocks failing to satisfy a larger request).
\end{definition}

\begin{definition}
    \textbf{Garbage Collection (GC):} An automated runtime technique that dynamically reclaims heap memory that will no longer be accessed by the application.
\end{definition}

\begin{remark}
    \textbf{Memory as a Directed Graph:} Garbage collection models heap memory as a directed reachability graph.
\end{remark}

\begin{definition}
    \textbf{Classical Garbage Collection Algorithms:}
    \begin{itemize}
        \item \textbf{Reference Counting:} Each block maintains a counter tracking incoming references. The block is freed immediately when the counter drops to zero. Cannot handle cyclic references without special cycle detection.
        \item \textbf{Mark-and-Sweep:} Tracing collector that identifies all reachable nodes by traversing from roots (mark phase), and then sweeps through all heap blocks to deallocate unmarked nodes (sweep phase).
        \item \textbf{Stop-and-Copy (Copying GC):} Splits heap memory into two regions (from-space and to-space). Reachable objects are copied contiguously into to-space, automatically compacting memory and eliminating external fragmentation.
        \item \textbf{Generational Collection:} Groups objects by lifetime into generations (young and old), collecting the short-lived young generation frequently and promoting surviving objects to the older generation.
    \end{itemize}
\end{definition}

\begin{example}
    \textbf{Mark-and-Sweep in Action:}
    \begin{itemize}
        \item \textbf{Mark Phase:} Begins at the root set and traverses all pointers (e.g., via depth-first search), setting a mark bit in the header of each reached block.
        \item \textbf{Sweep Phase:} Performs a linear scan over all heap blocks. If a block's mark bit is clear, it is freed; if set, its mark bit is reset to 0 in preparation for the next cycle.
    \end{itemize}
\end{example}

\begin{codeexample}
// Pseudocode for Mark-and-Sweep Collection
void mark(ptr p) {
    if ((b = block_of(p)) != NULL && !is_marked(b)) {
        set_marked(b);
        for (each pointer child in payload(b))
            mark(child);
    }
}

void sweep() {
    ptr p = heap_start();
    while (p < heap_end()) {
        if (!is_marked(p)) {
            if (is_allocated(p))
                free(p);
        } else {
            clear_marked(p);
        }
        p = next_block(p);
    }
}
\end{codeexample}

\begin{remark}
    \textbf{Conservative GC for C:} Because C is not type-safe, the runtime cannot distinguish whether an arbitrary memory word is a pointer or an integer. Conservative collectors (such as the Boehm-Demers-Weiser collector) assume that any word in the stack, registers, or heap whose numerical value corresponds to a valid heap address is a pointer, marking the referenced block as reachable to prevent premature freeing.
\end{remark}

\subsection{Memory Pitfalls}

\begin{remark}
    Because C allows direct pointer manipulation without automatic bounds checking or garbage collection, memory errors are common, difficult to diagnose, and can lead to severe security vulnerabilities.
\end{remark}

\begin{definition}
    \textbf{Common Memory Pitfalls:}
    \begin{itemize}
        \item \textbf{Dereferencing Bad Pointers:} Dereferencing an uninitialized pointer, a \texttt{NULL} pointer, or an arbitrary invalid address. This causes a segmentation fault (\texttt{SIGSEGV}) or corrupts arbitrary memory.
        \item \textbf{Reading Uninitialized Memory:} Assuming memory returned by \texttt{malloc()} is zero-filled. \texttt{malloc()} leaves the allocated block uninitialized with indeterminate garbage values. Memory must be initialized explicitly or allocated with \texttt{calloc()}.
        \item \textbf{Overwriting Memory (Buffer Overflow):} Writing past the boundaries of an allocated block due to off-by-one errors (e.g., \texttt{<=} instead of \texttt{<}), missing string null terminators, or calculating incorrect allocation sizes. This corrupts adjacent variables or heap metadata.
        \item \textbf{Referencing Nonexistent Variables:} Returning or storing the address of a local automatic stack variable. When the function returns, its stack frame is popped; the pointer becomes dangling, and subsequent function calls overwrite the data.
        \item \textbf{Freeing Blocks Multiple Times (Double Free):} Calling \texttt{free(p)} twice on the same pointer without an intervening allocation. This corrupts the allocator's free list data structures and can create exploitable security vulnerabilities.
        \item \textbf{Use-After-Free:} Accessing or modifying memory after it has been freed. The allocator may reallocate that block for another purpose, leading to silent data corruption or crashes.
        \item \textbf{Failing to Free Blocks (Memory Leaks):} Allocating memory on the heap and discarding all pointers to it without calling \texttt{free()}. Over time, leaked memory accumulates, exhausting system memory.
    \end{itemize}
\end{definition}

\begin{remark}
    \textbf{Best Practices for Safe Memory Management:}
    \begin{itemize}
        \item Always set freed pointers to \texttt{NULL} (\texttt{free(p); p = NULL;}), as calling \texttt{free(NULL)} is guaranteed to be safe and harmless in C.
        \item Use automated memory debugging and dynamic analysis tools such as \textbf{Valgrind} or AddressSanitizer (\texttt{-fsanitize=address}) during development to detect leaks and invalid accesses at runtime.
    \end{itemize}
\end{remark}
